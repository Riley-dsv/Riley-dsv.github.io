Introduction

There is a saying I love in IT :

Every modern infrastructure has three pillars; submarine cables, FOSS frameworks thanklessly maintained for 20 years by two unpaid developers and very old code running on very old machines no one even remembers.

Legacy systems are often portrayed as relics or obsolete software to be entirely replaced. However, replacing such systems is rarely a technical issue. The financial cost, the operational risk, the regulatory constraints and the business priorities that actually give value to the user often make a complete rewrite unrealistic.

This is why in the real world, you will find industries running on software older than the developers in the team. And those systems are running the world, from banking systems, to social security systems they are performing thousands of critical operations per day.

Mainstream is built around that observation.

I won't rewrite my bank's core system in Rust. Instead I will embrace the legacy COBOL and show how you can work with the legacy, not against it to create an efficient and modern event-driven architecture.

Goal

The goal of this phase was to define the stable contract of the pipeline before implementing anything. After all, even the most obscure legacy must obey some rules.

This phase focuses on the boundaries of the system: The legacy transaction format, the Kafka topics used by the future pipeline, the list of allowed transaction statuses, and the JSON schemas that describe the modern messages.

This is important because the architecture is your source of truth. Implementations will evolve over time, but the architecture must remain stable.

If a transaction file is defined as a sequence of fields separated by a pipe symbol, all future components interacting with that file must be able to rely on that definition. Without this stability, you can't build reliable and interoperable systems that last.

As it is common in system design, all decisions made during phase 0 are frozen, and become the source of truth. However, to avoid locking ourselves, backward compatible changes are allowed.

Even if in theory, you can still modify phase 0 afterward, but it require an explicit revision of the phase 0, and this is not something you want to do, unless there is a really good reason to do so.

Implementation

The main deliverables of this phase were documentation, schemas and sample data, as stated above, no runtime code for now. The current architecture is detailed on the project page. To avoid repeatition, this entry will focus on the core boundaries and data format defined in this phase.

Responsibility boundaries

  • COBOL handles legacy-style batch parsing and transformation.
  • Kafka handles event transport only.
  • Scala handles validation and enrichment.
  • Java handles persistence and REST API exposure.
  • PostgreSQL handles durable storage.
  • Phoenix handles user-facing realtime visualization only.

Legacy transaction format

Purpose

The legacy batch input is called : transaction_legacy.dat it is a fixed-width sequential file produced by the COBOL batch. Each line represents one raw transaction record. The file is designed to simulate a legacy batch input format before transformation into modern Kafka JSON events.

Design Principle

  • One transaction per line.
  • Fixed-width positional format.
  • Numeric fields are zero-padded on the left.
  • Alphanumeric fields are space-padded on the right.
  • Date uses YYYYMMDD.
  • Time uses HHMMSS.
  • Monetary values are stored as integers in the smallest currency unit.
  • The file only contains syntactically valid raw transactions for now.

Record Layout

Each records has a total length of 157 characters. Space betweens logical blocks are part of the format and must be preserved.

Record layout of the legacy transaction format
Field Start End Length Type Format / Rule
transaction id 1 32 32 alphanumeric unique transaction identifier, space-padded right if needed
filler-1 33 33 1 literal space
operation date 34 41 8 numeric YYYYMMDD
filler-2 42 42 1 literal space
operation time 43 48 6 numeric HHMMSS
filler-3 49 49 1 literal space
transaction type 50 52 3 alphanumeric example: TRF
filler-4 53 53 1 literal space
amount 54 65 12 numeric integer amount in smallest currency unit, zero-padded left
filler-5 66 66 1 literal space
currency 67 69 3 alphabetic ISO 4217, example: EUR
filler-6 70 70 1 literal space
sender iban 71 97 27 alphanumeric sender account identifier
filler-7 98 98 1 literal space
receiver iban 99 125 27 alphanumeric receiver account identifier
filler-8 126 126 1 literal space
reference 127 146 20 alphanumeric business label, space-padded right
filler-9 147 147 1 literal space
source system 148 155 8 alphanumeric example: BATCH001
filler-10 156 157 2 literal trailing spaces

Transaction topics

For Kafka to work properly we need something called topics, this is the fundamental organization unit for events or messages within Kafka. In Kafka, events are organized into topics, A topic acts as a named stream of messages that producers write to and consumers read from.

I personnaly created 3 main topics for my Kafka system :

transactions.raw

  • Produced by: COBOL Batch producer
  • Consumed by: Scala validation service
  • Purpose: Carries raw transaction events before validation
  • Payload contract: Raw transaction schema

transactions.validated

  • Produced by: Scala validation service
  • Consumed by: Java persistence / API service, Phoenix web interface
  • Purpose: Carries validated transaction events approved for downstream use
  • Payload contract: validated transaction schema

transactions.rejected

  • Produced by: Scala validation service
  • Consumed by: Phoenix web interface
  • Purpose: Carries rejected transaction events with rejection reason
  • Payload contract: Rejected transaction schema

Issues encountered

The main challenge here was not the code that didn't compile, but rather deciding what should be frozen, and what should remain flexible.

One might say, just freeze everything, but by doing so you lock yourself and prevent your application to actually evolve or correct if you ever make a mistake. The compromise was to freeze only the external contract: transaction format, Kafka topics, statuses, and JSON schemas. Internal implementation details remain free to evolve during the next phases.

There is also this invisible struggle, the second hardest thing in programming : Naming things, choosing name that reflects the intents, and sounds natural enough was a tidious task. Fortunately I had some help from a good website called Schema.org, it give vocabulary associated with a certain domain.
