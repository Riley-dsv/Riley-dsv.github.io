Context

before Java 16 and records, developers had to write long and verbose POJO Along with DTO and VO. This kind of boilerplate is verbose and prone to contain small errors. Even if modern tools like LLMs can generate this boilerplate automatically, it still need to be tested, maintained and documented. Artificially inflating the project size and test coverage without containing any real business logic. As an example, here is how we used to write this kind of boilerplate before : 


public final class Client
{
  private final String name;
  private final String company;
  private final String email;
  private final String phone;
  private final Integer fidelity;

  public Client(String name, String company, String email, String phone, Integer fidelity)
  {
    this.name = name;
    this.company = company;
    this.email = email;
    this.phone = phone;
    this.fidelity = fidelity;
  }

  public String getName()
  {
    return this.name;
  }

  // You have to write every other getters.

  @Override 
  public Integer hashCode()
  {
    final int prime = 31;
    int result = 1;
    result = prime * result + (( name == null ) ? 0 : name.hashCode());
    result = prime * result + (( company == null ) ? 0 : company.hashCode());
    result = prime * result + (( email == null ) ? 0 : email.hashCode());
    result = prime * result + (( phone == null ) ? 0 : phone.hashCode());
    result = prime * result + (( fidelity == null ) ? 0 : fidelity.hashCode());
    return result;
  }

  @Override 
  public Boolean equals(Object obj)
  {
    if ( this == obj ) return true;
    if ( obj == null ) return false;
    if ( getClass() != obj.getClass() ) return false;
    Client other = (Client) obj;
    if (name == null)
    {
      if (other.name != null) return false;
    }
    else
    {
      if (!name.equals(other.name)) return false;
    }
    // And it goes for every member you added in the class
    if (fidelity == null)
    {
      if (other.fidelity != null) return false;
    }
  else
  {
    if (!fidelity.equals(other.fidelity)) return false;
  }
    return true;
  }

  @Override 
  public String toString()
  {
    return "Client : name=" + name + ", company=" + company + ", email=" + email + ", phone=" + phone + ", fidelity=" + fidelity;
  }
}

This was a boilerplate back then, for the sake of clarity and brievety, I did trimmed the longest part.

What is a record ?

In Java a Record Class is a special kind of class. It is final by default preventing inheritance via extends, each fields are set private final by default making them immutable. They contain default getter in the form of accessor methods, constructor, overridden toString(), equals() and hashCode() methods. All of this is generated by the compiler during compile time. While is is prohibited to extend a Record with another class or record, it is totally fine and licit to implement an interface in a record.

Records can define their own methods and can be generic, just like regular classes, making it way easier to to adopt in existing codebases.

This also allows means records are not limited to being passive data carriers. They can encapsulate domain logic alongside the data they operate on.

Canonical Constructor

While records are often introduced as a way to reduce boilerplate ( I do not make exceptions ), they also provide a convenient location to enforce invariants and therefore declare your intents.

Every record defines a canonical constructor whose parameters match the components declared in the record header. However, you can also describe your own constructor, and place your invariants checks in it. 


public record Client(String name, String email)
{
  public Client
  {
    Objects.requireNonNull(name);
    Objects.requireNonNull(email);

    if (name.isBlank())
    {
      throw new IllegalArgumentException("Name cannot be blank");
    }
  }
}

The constructor behave exactly like a regular class constructor and get called for every newly created instance. Since you remove the need to assign record components to internal members, you have now just the right place to centralized your invariants, and avoid having logic validation scattered through the codebase.

Limitations

Some might wonder, if records are so good, why do we still uses regular classes ? If you remember, I wrote earlier that Records are implicitly final. This prevent them from being part of inheritance hierarchies, locking some very useful design patterns.

This also means concept such as abstract records can't possibly exists, if you ever tried to create a class in java with abstract final the compiler, must have complained. When polymorphism, inheritance or inheritance based design patterns are required, a traditional class remains the tools for this job.

Conclusion

Records are one of the many features introduced in recent Java Releases to reduce complexity and improve the language ergonomics as part of DX.

While they cannot replace every class, they provide a specialized and expressive way to declare immutable data while keeping validation logic close to the data it protects.

As with many language features, they come with tradeoffs. Their inability to participate in inheritance hierarchies makes them unsuitable for some designs, but for value-oriented types, DTOs and immutable domain objects, they provide a cleaner and more maintainable alternative to traditional POJOs.
