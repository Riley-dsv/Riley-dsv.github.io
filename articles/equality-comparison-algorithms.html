Context

Comparison is the main thing you use in multiple languages, and ECMAscript is no exceptions. However, ubknownst to most of the developers ECMAscript use different comparison algorithms.

Today, we will dip a toe in the ECMAscript specification, and focus on the algorithm comparison explain what do they compare, how and who is actually using them.

Abstract equality comparison algorithm

Historical ECMAscript comparison algorithm. Used when you compare stuff using double-equal (==). In a normal situation it simply compare values. Such as : 


3 == 3 -> True
"String" == "String" -> True

But in certain situations, the Abstract Equality Comparaison Algorithm will implicitly convert types. This can happens with Numbers, Boolean, Primitives and Nullables. Such as : 


3 == "3" -> ( toNumber on "3" ) -> 3 == 3 -> True
[1] == "1" -> ( toPrimitive on [1] ) -> "1" == "1" -> True

The case of boolean is quite simple. Coercion change True to 1 and False to 0.


true == 1 -> True
false == 0 -> True

With all of this, you can explain the most famous example of JS weirdness : [] == 0. If you break it down, you have an empty array, compared against a number type. [] is converted to the number 0 you can verify it using the following Javascript instructions in a REPL :


const arr = []
Number(arr) // Exepcted output : 0

Ok this might look weird at first Glance, how does it prove anything ? I mean, I just called a Number function no ? No. I called Primitive operation on the object. This is what the ECMAscript engine is expected to do, if you refer to the official ECMAscript documentation :

1. If Type(x) is Object and Type(y) is either String or Number, return the result of the comparison ToPrimitive(x) == y.

ECMAScript specification

Looking at the ToPrimitive table, the Object seek a PreferredType a hint about the type he seek. Here the hint is the type of y. The type of y being a Number, Javascript will call the Number primitive method on the object. We end up with 0 == 0 and therefore returns true.

Now your turn, if you want to see if you understood, what is the output of : -[-3] == “3" ?

There is a kind of coercition also happening with undefined. Indeed, using the Abstract equality, null and undefined become equal. Meaning if you want to check for null and undefined at the same time. you just need to use Abstract Equality.


if ( foo == null || foo == undefined ) ⇒ if ( foo == null )

Strict Equality Comparison Algorithm

The Strict Equality Comparison is used when you compare using triple equal (===). This is a more recent algorithm, it has been made to ignore type coercition. This disable the undefined == null tricks as well as the Boolean as Number principle.

However, you ensure data type integrity. If your database is supposed to return number and you get a string, no coercition will happen therefore, an exception could be raise or some sort of fallback could happen. But this is up to you to implement it.

Same Value Comparison Algorithm

A less known Comparison algorithm and that's sad. Because if you ever used data structure in JavaScript or TypeScript you may have encounter this behavior. ECMAscript follow the IEEE-754 about floating point conversions, there is a lot about it like how integer and floats are supposed to be represented, but only two principles are interesting for us : NaN and +0/-0 ( Called Two-zeroes ).

NaN stands for Not A Number, IEEE-754 defines it as a Number that you can't mathematically express. Think of stuff like :

NOTA: Remember, here we are speaking about IEE-754 Specification, not ECMAscript real implementation.

Two Zeroes is a logical result of how numbers are formatted under the IEEE-754. I won't get too deep in the detail, you just must know that each number contain a sign bit. If it is set to 0 the number is positive, if it is set to 1 the number is negative. The same rule apply for 0, this is why it exists a positive 0 and a negative 0 or Two-Zeroes.

Under normal circumstances, Using either Abstract Equality Algorithm or Exact Equality Algorithm. The result will follow the IEEE-754 so :

Comparing NaN to itself will return false no matter what, and it makes sense NaN is an impossible number, you can't compare it to anything. However +0 will always be equal to -0. Because they are in fine the same numbers.

Now that this is cleared up, let's see the implication of the preceding statement. let's assume you write something like this :


const map = new Map()
map.set(NaN, "John");
map.get(NaN);

By strictly following IEEE-754, get would return undefined. The same could happen with a Set. Fortunately, Javascript use another comparison algorithm, it just check if two values are the same, not if they are actually mathematically equal.

Best is example is for two zeroes, even if they are the same numbers. they do not produce the same mathematical results, for example : 


1 / +0 // Infinity
1 / -0 // -Infinity

This difference is sufficient enough to have the same needs as NaN if you set something in a Map as -0 you must differentiate them. To check this, you can use the internal JavaScript method Object.is 


Object.is(+0, -0) // False
Object.is(NaN, Nan) // True

As an additional notes it exist a fourth Comparison algorithm. The Same Value Zero Comparison Algorithm. It works the same way as the Same Value Comparison, but it keeps the equality of +0 / -0. It's really specific but there is a use in JavaScript the includes methods for example : 


[-0].indexOf(+0)    // Expected output : 0
[NaN].indexOf(NaN)  // Expected output : -1
[NaN].includes(NaN) // Expected output : true
[-0].includes(+0)   // Expected output : true
